# HTMX write routes: API readiness census

Status: **census only, nothing scheduled.** Taken 2026-09-24 against
`origin/staging` (`6b4fd6fb`). Line numbers are the `@bp.route` decorator
at that commit; they will drift, the route names will not.

## Why this exists

The `/htmx/` routes are a UI backend: form-encoded input, `HX-Trigger` /
`HX-Redirect` success responses, validation errors re-rendered as HTML.
They are not an API and should not become one via content negotiation.
The layers *under* them are general — `sam.schemas.forms`, the
`webapp/api/access_control.py` decorators, `sam.manage`, and model
`create()` / `update()`. A JSON endpoint is cheap exactly when a handler is
a thin adapter over those layers, and expensive when a business rule lives
only in the route module.

This census records which is which, so that as htmx grows we know what API
functionality could follow cheaply and where the extraction work sits.

## Rubric

| Tier | Meaning |
|---|---|
| **CLEAN** | schema load → FK checks → one call into `sam.*` (manage function or model method). A JSON adapter is ~15 lines. |
| **GLUE** | the domain op is below the webapp, but a business rule / precondition / derivation lives in the route module. Movable with modest effort. |
| **STUCK** | the mutation itself is assembled in the route (direct ORM writes, multi-step composition, inline rules); there is no single domain function to call. |
| **UI-ONLY** | no API meaning: mail previews, form re-renders, impersonation, UI cache buttons. |

The litmus test: could the route be rewritten as a JSON adapter over the
same schema + decorator + domain call? The reference adapter is
`POST /api/v1/projects/<projcode>/members` (`src/webapp/api/v1/projects.py`),
which reuses `AddMemberForm` + `add_user_to_project` from the htmx
add-member modal.

## Extraction clusters (ranked by likely API demand)

### 1. Allocation lifecycle refusal rules — GLUE, one security-relevant

Routes: renew, extend, exchange, propagate-to-remaining
(`src/webapp/dashboards/admin/projects_routes.py`).

| Helper in the route module | Rule it holds | Target |
|---|---|---|
| `_renew_preconditions` | refusal messages; "nothing ok unless `replace_existing`" | `sam.manage.renew` |
| `_extend_shortening_error` | refuse unless new end > latest current end (the domain only skips silently) | `sam.manage.extend` |
| `_exchange_candidates` + `clean()` overdraft check | both ends scoped to the project subtree at `active_at`; usage-based overdraft | `sam.manage.allocations.exchange_allocations` |
| propagate route body | `_has_any_alloc` filter + `is_inheriting` refusal | `propagate_allocation_to_subprojects` |

⚠️ **Exchange is security-relevant.** The subtree scoping is the defense
against forged allocation ids, and the overdraft rule exists only in
`clean()`. An API that called `exchange_allocations` directly would skip
both.

Side effect an API must replicate: `_maybe_notify_renewal` (renew/extend
lead mail) — belongs beside `sam.queries.lifecycle_notices`.

### 2. Project create — STUCK, duplicated

`htmx_project_create`'s `_do_action` does the whole build inline: projcode
auto/manual branch, GID draw (`GidAllocation.allocate_next_gid`),
`Project.create`, contract/org links, per-facility `CREATE_PROJECTS` check.
`src/sam/xras/handlers/new.py` hand-copies the same steps. Target: a
`create_project(...)` in `sam.manage.projects` that both call.

Runner-up in the same file: `htmx_project_update` (GLUE) — governance-field
stripping for non-admin stewards and the `active` / `charging_exempt`
checkbox reads from raw `request.form`.

### 3. XRAS remediation target resolution — GLUE ×~12

`src/webapp/dashboards/allocations/xras/remediation.py`. Every write op
already lives in `sam.manage.xras_remediation` and writes its own audit row
and patches the index cache. What the webapp holds is the *target
resolution*: `_editor_target`, `_action_context`, `_roles_context` here plus
`_live_request` / `_entry` / `_impersonation` in `xras/_shared.py` — resolve
`request_id` and the XA-USER to impersonate from a live XRAS read. One
resolver in `sam.manage.xras_remediation` turns ~12 routes CLEAN.

Also: `xras_request_delete` is STUCK (projcode-scoped loop over the live
family with per-line `resolve_pi` and partial-failure aggregation) — wants a
`delete_request_family`. `xras_merge` and `xras_role_add` keep fail-closed
`get_person` existence checks in `clean()`.

### 4. XRAS pending-activation — STUCK/GLUE, duplicated with the scheduler

`src/webapp/dashboards/allocations/xras/lifecycle_routes.py`.
`_record_activation_event` is a proto-domain helper in the route module.
`xras_activate` composes `project.reactivate()` + the event in the route;
`xras_notify` holds send-first-record-second, the "nothing delivered → no
event" rule, and the `notified_to` format — which
`src/scheduling/tasks/xras_notices.py` (`_record_notified`) re-implements
because the scheduler cannot import the webapp. Target:
`sam/manage/xras_activation.py` (new), used by both.

### 5. Event lifecycle and invite links — domain code living in the webapp

`src/webapp/dashboards/event_lifecycle.py` (`create_event`,
`resolve_sponsor`, the edit rules: past-deadline-only-if-changed, sponsor,
`listed` gated on `can_create_events`) and
`src/webapp/register/invite_mail.py` (`send_invite_links`, which writes
`invite_sent_at`). Imported by `project_invites.py`, `admin/events_routes.py`,
`register/blueprint.py`, `status/blueprint.py`. Target:
`sam.manage.account_requests`, with an `actor` parameter instead of
`current_user` and a domain error instead of `FormError`. The handlers,
`roster_preview`, and the memoized upcoming-events listing stay in the
webapp.

### 6. Webapp code the CLI and scheduler reach into

- `src/webapp/api/xras/recheck.py` (`recheck_action`) is a domain op outside
  `sam/`; `sam-admin xras --recheck` boots `create_app()` just to call it.
- The account digest exists twice: `account_requests_digest`
  (`src/webapp/dashboards/admin/account_requests_routes.py`) and
  `src/scheduling/tasks/account_queue_digest.py`. They have already diverged
  (see *Found along the way*).

### 7. `system_status` outage writes — STUCK ×4, duplicated

`src/webapp/dashboards/status/blueprint.py` (create / edit / resolve /
delete outage) builds `SystemOutage` rows inline and commits directly;
`src/webapp/api/v1/status.py` (`POST /outage`, `PATCH` / `DELETE
/outages/<id>`) does the same with its own validation and no UTC
normalization. Target: one outage write module under `src/system_status/`
that both call — and the place to decide whether resolve sets `end_time`
(neither does today).

### 8. `CrudSpec` → a JSON generator

The 36 generated routes are all CLEAN at the domain level
(`src/webapp/dashboards/admin/crud.py`). `model`, `*_schema`,
`*_fields` / `*_kwargs`, `*_permission`, `actions`, `id_param` carry over
directly; `triggers`, `*_context`, `*_template`, `noun` are UI-only. A
parallel JSON generator is mechanical once the spec gains:

1. **`dump_schema`** — response serializers exist only for Resource,
   ResourceType, and Contract (summary).
2. **PATCH semantics** — form schemas use `active = Bool(load_default=False)`
   because an unchecked checkbox is absent; a JSON body omitting `active`
   would deactivate the row. Load `partial=True` and forward only keys
   present, as `PUT /api/v1/allocations/<id>` already does.
3. **`fk_checks`** — no spec validates FKs today (`parent_org_id`,
   `institution_type_id`, `facility_id`, `panel_id`, ...); the DB constraint
   catches it, as a generic error.
4. **Error mapping** — model `ValueError` → 400, `IntegrityError` → 409.
5. **A `delete` callable** — soft-delete is hardcoded; Resource, Machine,
   Queue, Contract retire by date instead (bespoke routes today).
6. **Auth** — `login_or_token_required(Permission)` rather than
   `login_required` + `require_permission`.

## Cross-cutting facts for an API author

- **Cache invalidation is free.** `src/webapp/audit/events.py` registers a
  session `after_commit` listener that clears the `flask` cache on every
  commit, so a JSON endpoint inherits it. (The queue routes'
  `invalidate_queue_cache()` is belt-and-braces.)
- **Mail is not free.** Renew/extend lead notices, invite links, rejection
  mail, and XRAS notify all run in handler `after_commit` / route bodies. An
  API must call them explicitly — another reason to move them into `sam/`.
- ⚠️ **API-key auth bypasses the Permission check.** The Basic-Auth path of
  `login_or_token_required` accepts any valid key. Fine for today's
  read-mostly `api/v1`; a prerequisite to fix before exposing any write in
  this census to scripts.
- **Input read outside the schema** (would need adding to the schema for an
  API): `break_inheritance` (admin edit-allocation), `action_<project_id>`
  (notify-project), `stage` (XRAS resource edit), `request_number` /
  `return_to` (XRAS overrides), `force` (XRAS notify), the
  `listed_present` / `invite_only_present` sentinels in `event_lifecycle.py`,
  and `_parse_active_at_arg`, which silently falls back to today on a bad
  date.

## Found along the way (not fixed here)

- **Resource-type Deactivate always fails (read, not clicked).** The
  `resource-type` spec in `admin/resources_routes.py` inherits the default
  `actions=('edit', 'create', 'delete')`. `ResourceType` has no `active`
  column and `ResourceType.update()` accepts only `grace_period_days`, so
  `handle_htmx_soft_delete` raises `TypeError` and returns 500; the button
  is live in `resources_card.html`. Fix: `actions=('edit', 'create')`, drop
  the button, regen the route-map snapshot.
- **Digest route vs. digest task.** The Send button checks neither
  `SAM_TASKS_ACCOUNT_MAX` nor `raise_if_disabled`. The cap matters less for
  an operator who saw the count in the preview, but with `NOTIFY_ENABLED`
  false the send records `suppressed` and the route answers *"A digest
  already went to NUSD today"* — a misleading message.
- **User-dashboard edit-allocation is not partial** (`user/blueprint.py`):
  it always overwrites amount / end date / description, unlike the admin
  form and the API. Harmless while the form always posts all three.
- **Two cache-category lists**: `_VALID_CACHE_CATEGORIES` in
  `admin/configuration_routes.py` vs. `caching.categories` in the API.

## Keeping it current

- A new htmx write handler should put its business preconditions in `sam/`
  and have `clean()` map the domain error to a `FormError` — not define the
  rule. That keeps the handler CLEAN by construction.
- When a cluster is extracted, re-run the census for the files it touched
  and update the headline counts.
