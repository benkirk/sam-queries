{# Resolve identity — the assisted merge decision, rendered into #auditDetailsModalBody and re-rendered in place on a validation error. Context: username, person, candidates[], write_enabled, post_url WHY THIS IS A MERGE AND NOT AN "UNRECONCILE" The obvious fix — flip `isReconciled` back to false so the placeholder rejoins XRAS's own unreconciled queue — does not exist. That endpoint returns 200 and silently drops the parameter; a button wired to it would be the worst kind, green and inert. Reconciliation in XRAS *is* a merge, so the remedy is to complete the merge that never happened. WHY NOTHING IS PRESELECTED WHEN THERE IS MORE THAN ONE CANDIDATE Measured on real data: one human had two live XRAS identities differing only by email and organization — a university address and an NCAR-staff one. A name match picks between them arbitrarily, and merge DELETES the loser and moves the placeholder's roles onto the winner. So the safe key is email and organization, never the name, and the operator chooses. A single STRONG match (rank 0 — the email resolves to it) is the opposite case, nothing to choose between, so it is shown read-only as the confirmed target (no radio); Cancel rejects it. A single WEAK match still gets a radio — a name-only hit is not trustworthy enough to confirm for the operator. Deliberate deviation from the plan: the override is a plain text input, not an FK picker. A picker over SAM users would return a SAM username, and the merge target is an XRAS identity — the two are not the same namespace. The handler resolves whatever is typed against XRAS and refuses if it does not already exist, because the API CREATES an unknown target rather than failing. #} {% from 'dashboards/fragments/form_fields.html' import text_field, textarea_field, form_errors_panel with context %}
