Popover strings (rich=True) may contain simple HTML. #} {# Rolling consumption rate (popover) #} {% macro g_rolling_rate() -%} Charges over the last 30/90 days compared with the prorated steady-state rate — the pace needed to spend exactly the allocation over its period.
• 100% = on pace
• <80% — running cold
• 80–115% — near steady
• >115% — running hot
A dashed line marks an optional user-set limit; the bar turns red once the rate crosses it. {%- endmacro %} {# Consumption-rate limit (popover) #} {% macro g_threshold_limit(window=None) -%} Sets a hard limit on a project's resource consumption rate. Exceeding this threshold prevents the system from scheduling new jobs until usage has decreased — useful to avoid exhausting a project's resources too early in the allotted period.

Recommended limits:
• 120% over 30 days
• 105% over 90 days {%- endmacro %} {% macro g_shared_pool() -%} This allocation draws from a pool shared with other projects in the same allocation tree — every member carries the full pool amount. The bar shows total pool consumption; the lighter inner segment (and "(N yours)") is this project's own contribution. {%- endmacro %} {# Allocation trees: shared / standalone / carve-out / unallocated One vocabulary for the admin Allocations tab and its forms. A "shared" allocation is linked to its parent (a pool copy); a "standalone" one has its own amount; a standalone sub-project allocation with a distinct amount is a "carve-out" of its parent's total; what the parent has not yet carved out is its "unallocated" remainder. #} {% macro g_shared_alloc() -%} This allocation is linked to its parent project's allocation and mirrors it: same amount and dates, drawing from the same shared pool. Edits to the parent are applied here automatically. Usage by this project still rolls up to the pool's total consumption. {%- endmacro %} {% macro g_standalone_alloc() -%} This allocation has its own amount and dates — it is not linked to a parent allocation. When it sits under a parent project's allocation for the same resource, it carves out part of the parent's total. {%- endmacro %} {% macro g_unallocated() -%} The part of this allocation not yet assigned to sub-projects: its amount minus the sub-project carve-outs on the same resource. Sub-projects sharing the pool (linked, or carrying the same amount) do not count against it. Assigning it to a sub-project increases that sub-project's own allocation without changing this one. {%- endmacro %} {% macro g_exchange() -%} Moves an amount between two standalone sub-project allocations on the same resource — one goes down, the other up, so the allocation tree's total is unchanged. Dates are not changed. {%- endmacro %} {% macro g_renew_vs_extend() -%} Renew creates a new allocation period, mirroring the current amounts and tree structure. Extend only moves the end date of the existing allocations — amounts are unchanged. {%- endmacro %} {% macro g_renew_scale() -%} Multiplier applied to each renewed amount — 1 renews at the same size, 0.5 halves it, 2 doubles it. {%- endmacro %} {% macro g_detach() -%} Breaking the link makes this allocation standalone: edits to the parent allocation no longer apply here, and its amount becomes a carve-out of the parent's total. Usage still rolls up to the parent project, and the parent's amount is not adjusted. {%- endmacro %} {% macro g_elapsed() -%} Marks how far through the allocation period today falls — a pacing reference, not a usage threshold. Usage to the left of this line means you're under pace. {%- endmacro %} {% macro g_usage_bar() -%} The filled portion is consumed usage against the allocated total. On a shared allocation, the lighter inner segment (and "(N yours)") is this project's own share of a pool drawn down by sibling projects too. The vertical marker shows how far through the allocation period today falls — a pacing reference, not a threshold. {%- endmacro %} {# Units (tooltips) #} {% macro g_au() -%} Allocation Units — the charged cost of compute, weighted by job size, node type and queue. Drawn down from your allocated total. {%- endmacro %} {% macro g_core_hours() -%} Core-hours = cores used × wall-clock hours. The raw usage measure, before allocation-unit weighting. {%- endmacro %} {% macro g_cpu_hours() -%} CPU-hours = CPUs used × wall-clock hours, measured from PBS job records. Close kin to Core-hours, but a different source — job history, not charge summaries — so the two won't tie out exactly. {%- endmacro %} {% macro g_charges() -%} Allocation units drawn down by this activity over the selected date range — the billed amount, not a job count. {%- endmacro %} {% macro g_tib() -%} Tebibyte (2⁴⁰ bytes ≈ 1.1 TB). Storage allocations are sized in TiB. {%- endmacro %} {% macro g_tib_years() -%} TiB held × years held — storage capacity integrated over time, the way disk allocations are charged. {%- endmacro %} {# Transaction & adjustment types (popover) #} {% macro g_txn_types() -%} {# Popover HTML collapses source newlines, so use explicit

• Pending — eligible and waiting in the queue

The current blocks above show only affiliations in effect today; these are kept for history, newest first. {%- endmacro %} {# Contract currency on the project card (popover) #} {% macro g_contract_status() -%} Every contract ever linked to this project is listed, current ones first — an expired grant is still the project's funding provenance.

• solid — the project itself is inactive (deactivated)
• outline — the project is still active, but this user's membership has ended. {%- endmacro %} {# XRAS Remediations: pending work vs. everything (popover) #} {% macro g_xras_pending_work() -%} Off — pending work only. The same population as XRAS admin’s Recent submissions: a request with an action the last sweep checked that is still in review (Submitted / Under Review), or Approved and not yet posted to SAM — no SAM project yet, or arrived after the repoint with no action-log row. No date filter: an old approval nobody pushed is exactly the point.

This is the only view with “not checked” rows, so Check all lives here. {%- endmacro %} {# XRAS Remediations: the mnemonic-unblock strip (popover) #} {% macro g_xras_mnemonic_strip() -%} Ranks the organizations and institutions whose missing mnemonic code blocks the failing pushes in view. SAM mints a project code from the PI’s org (internal) or institution (external) mnemonic; with none linked, posting a New is rejected (a posting error, HTTP 422) and the request waits. Create the code in Admin → Organizations and the next sweep drops the org from this list. The count is the pushes that one link unblocks; PIs with no current affiliation need a membership fix instead and are counted apart. {%- endmacro %} {# XRAS Remediations: the contract-blockers strip (popover) #} {% macro g_xras_contract_strip() -%} Ranks the grant numbers SAM holds no contract for among the failing pushes in view. The New handler links a contract, never creates one, so a number SAM has never seen is rejected at posting (a posting error, HTTP 422) until a contract row exists. Each number opens Admin → Contracts with the form seeded from XRAS (title, dates) — look-up mode for NSF awards, manual for project references. A number that would tie against existing rows is a spelling variant to reconcile, not a row to create, and gets no link. Rows created since the sweep drop out on their own. {%- endmacro %} {# XRAS Remediations: the identity strip (popover) #} {% macro g_xras_identity_strip() -%} Ranks the ARC placeholders (<name>-user-<token>) among the requests in view whose email SAM already holds on an active account. Every active SAM account resolves in XRAS, so that account is a merge target already: merging deletes the placeholder and moves its roles onto the real username, and XRAS sends the real username from then on. The match is the email, never the name — a name-only match can pick the wrong one of two real people. Placeholders whose email SAM does not hold still need an account created first; merged rows drop out on their own. {%- endmacro %}
