Measure first, then fix what the measurement points at.

Where we started

  • One production day, 2026-09-02: 5,457 requests in 16 hours, none failed.
  • The median request was fast: 179 ms.
  • The tail was slow: p95 2.95 s, p99 6.7 s.
  • The tail was a few batch endpoints, serving large JSON to machines: directory_access averaged 6.9 s, and the Casper fstree 1.7 s.
  • So the work went where the time was, not where it looked slow.

The slow endpoints’ callers are ssg (fstree, directory_access, every 5 minutes), the collectors and XRAS. Fstree Derecho averaged 1.1 s; the GPU variants 150-350 ms.

The surprise: checking keys

def _key_matches(username, password, stored_hash):
    key = (username, stored_hash, sha256(password))
    seen = _VERIFY_CACHE.get(key)
    if seen is not None and (now - seen) < ttl:
        return True
    if not _bcrypt_matches(password, stored_hash):
        return False
    _VERIFY_CACHE[key] = now
    return True
  • Every API-key request spent about 260 ms checking the key. That was all its CPU.
  • Now a good key is remembered for 5 minutes; a wrong one always pays.
  • 32 clients, on dev: 12.5 → 180 requests a second, median 2.0 s → 0.16 s.

src/webapp/utils/api_auth.py:114-130, trimmed (the TTL switch and the size bound removed). bcrypt at cost 12. API_KEY_VERIFY_TTL defaults to 300 s, per worker process, at most 256 entries; rotating a key changes stored_hash, so old entries miss. #561. Measured on samuel-dev, 2026-09-13, /api/v1/users/<u> through the Ingress (DEV_LOAD_CAMPAIGN.md:45-58, 186-200). After the fix the median server time was 37 ms: cpu 7.5 + sam 26.9. The bottleneck moved to the database, where it belongs.

The read model, in code

oldest = min(r.refreshed_at for r in rows)
if now - oldest > cfg.max_age:
    return Lookup(None, 'too-old')            # compute live
stale = {t for t, stamp in stamp_of.items()
         if stamp >= oldest_by_tree.get(t, oldest)}
if not stale:
    return Lookup(rows, 'ok')                 # serve the table
if len(stale) > cfg.patch_max_trees:
    return Lookup(None, 'too-many-stale')     # compute live
# else: recompute the changed trees in memory, serve the rest
  • One row per allocation: used, remaining and charges, rebuilt every hour.
  • Rebuilt by the same function the live path calls, so the two cannot disagree.
  • Each log line says which: rm=served, rm=patched:2, rm=live:too-old.

src/sam/queries/allocation_state.py:378-396, trimmed. Table account_allocation_state in SAM MySQL: allocations active or ended within 90 days, 4,823 rows in prod (2026-09-11). Feeder: src/scheduling/tasks/refresh_allocation_state.py, hourly, lands about :07; it calls project_allocation_state(), which runs the dashboards’ batched builder. Gate: on only with READ_MODEL_ENABLED (prod “1”), rows from today, no older than 2 h (one missed run tolerated), at most 250 changed trees. A read never writes the table. Readers: the dashboards, the allocations page, fstree, and the project allocations and charges APIs. Design and record: docs/plans/implemented/READ_MODEL.md; #534, #543, #546 (2026-09-09 to 09-11).

Static files: one rule

  • Every link to a static file carries a hash of its content: dashboard.css?v=…
  • With the hash, the browser keeps it for a year. Without, for an hour.
  • Before, 2026-08-17: 87.5% of all requests were static files, and 96% of those only asked “unchanged?”.
  • After: static requests per page request fell from 7 to under 1 (0.3 by 2026-09-02).

CLAUDE.md §11; src/webapp/utils/static_assets.py; #453. Before: nwc1, one pod, 4h37m; Bootstrap was revalidated ~145 times in 4.5 hours. After: 7.0 to 0.5-0.9 within ~40 minutes, holding at 0.76; a second roll with identical hashes gave 0.36, so browser caches survived the deploy. A content hash, not mtime: a rebuild restamps every mtime. PROD_PERF_WATCH.md:19 for 0.3. Gate: tests/unit/gates/test_static_assets.py.

⚠︎ Cache traps

  • No targeted invalidation for a cached page: any database commit clears them all.
  • Charts are keyed by their data, not their code. After a visual change, refresh them.
  • After a deploy, refresh the narrowest category: sam-admin cache --refresh.
  • A refresh under load is a stampede: 32 cold chart renders took 16.5 s each (median). Nothing yet stops two requests building the same entry.

†Next: invalidation that follows the deploy, so nobody has to remember.

Commit hook: _flush_view_cache, src/webapp/audit/events.py:192-206; collectors commit every few minutes, so most page entries die well before 5 minutes. delete_memoized does nothing on a view. Categories: flask, chart, usage, scans, jobs, awards, xras_api (src/webapp/caching/init.py). Rendered HTML also keeps old ?v= tags until it expires. The stampede: DEV_LOAD_CAMPAIGN.md finding D, 2026-09-15; no dogpile lock. The follow-on (Ben, 2026-10-02, on the plan’s fix-later list): a code version in the code-dependent keys, a single-flight lock per key, pre-warming hot keys, targeted view invalidation.

The shape of a query: split and assemble

  • The directory export was one join. Each user fanned out 14 ways: accounts, allocations, phones, institutions, organizations. About 135,000 rows, grouped back down.
  • Now it is 12 small queries, one per kind of fact, stitched together in Python.
  • About 4× faster (1.5 s → 0.38 s on a production copy), and the same plan on every database.
  • Same answer out, checked by the parity harness.

src/sam/queries/directory_access.py:115-125 and 364-405: one DISTINCT membership query, then bulk phone, institution, organization, key-resource, override and shell lookups (8), plus the group populator’s 4. #492, in production 2026-09-03. Plan stability: an intermediate version that kept the overrides in SQL exploded to over 1M rows on the test database while fine on another, so rewrites are timed on both. Dev Postgres: 415 ms, 12 queries (DEV_LOAD_CAMPAIGN.md:28). No production after-number was recorded. Byte-identical except ~21 users whose duplicate phone rows had stray whitespace, now trimmed. Benchmark: tests/perf/test_directory_access_latency.py.

Still slow, and known

  • The all-facility pace chart: 9–11 s cold, 0.25 s warm. Accepted.
  • A year of jobs over a wide project tree: 2.6 s the first time.
  • Deploys refresh the caches by hand, and a cold refresh under load stampedes.
  • Disk-scan queries run in worker threads, so their time shows as waiting.

Pace chart: #691, prod 2026-10-01. Jobs: DEV_LOAD_CAMPAIGN.md:170-176; 30 days is ~160 ms, and it is cached after the first view. Caches: the follow-on on the Cache traps slide. Threads: #655, open; the request timing records only in the request’s thread. Also outside SAMuel: the shared Ingress drops a new connection for ~8 s every minute or two (DEV_LOAD_CAMPAIGN.md finding F), handed to the platform team.

TL;DR - performance

  • Measure first: every request logs its CPU and its time in each database.
  • Pin the count: make perf and the production watch catch an N+1 early.
  • The read model serves allocation usage from one row each, rebuilt by the live code.
  • Cache with a known key, and refresh after a deploy.
  • Shape the query, index the big tables: seconds became milliseconds.
  • Still slow is written down, and next is cache invalidation that follows the deploy.
