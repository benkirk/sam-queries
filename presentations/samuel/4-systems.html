Two apps, one database

  • Legacy SAM: Java on Tomcat, on sam-tomcat, behind sam.ucar.edu. Still running.
  • SAMuel: Python on CIRRUS, at sam.hpc.ucar.edu. Production SAM.
  • Both read and write sam-sql: one MySQL VM, run by CISL, with no replica.
  • They will overlap for a while, by design.
  • Until legacy retires, SAMuel gives way: it keeps the rows legacy reads, rather than deleting them.

†sam-app is a third host: it runs the identity helpers, not the Java app.

sam.ucar.edu is a load-balanced address in front of two Apache proxies that forward to Tomcat on sam-tomcat.ucar.edu (SAM 2.0.4). sam-app.ucar.edu runs the LDAP replica, the transformer and sam-ldap-syncd as rootless podman containers. Sources: sam-queries docs/plans/SAM_LDAP_SYNCD_REFERENCE.md §2.5 and docs/plans/LDAP_SYNC_API.md. Giving way, 2026-10-02: unsetting a fair-share override deleted a facility_resource row, and legacy’s fair-share tree for Derecho came back empty (#698). The row now stays, with a NULL value. An audit of every SAMuel delete on a table legacy reads followed (#699, docs/plans/HARD_DELETE_AUDIT.md): a superseded allocation is shortened rather than left live, and the disk-root hard delete is gone.

We don’t own the schema (yet)

Legacy’s

  • Flyway migrations up to V38, applied by hand.
  • 92 of our 108 modeled tables were created by them.
  • The newest serve the identity sync, and they can drop a column we read.

Ours

  • 16 tables SAMuel added: notifications, account requests, roles, the XRAS ledgers.
  • Plain DDL in scripts/sql/, and never an ALTER on a legacy table.
  • The ORM follows the database; schema-validation tests catch drift.

Counted 2026-09-30: every CREATE TABLE in legacy’s src/main/resources/db/migration against the ORM’s metadata. 92 + 16 = 108, every modeled table accounted for. Legacy applies its migrations with tools/dbmigrate.sh (mvn flyway:migrate), not at startup. CLAUDE.md’s rule: the database is the source of truth; don’t modify the SAM schema. That is why the SAM schema is not under Alembic (Part 3), and why Postgres in prod waits on legacy’s retirement.

⚠︎ Don’t let this happen to you… again

  • 2026-08-10, the schema edition: the identity-sync cutover shipped legacy migration V37, dropping two columns from users and seven other tables.
  • SAMuel’s ORM still selected them. Every page returned 500 for ~20 minutes, while all three health probes said 200: SELECT 1 can’t see a missing column.
  • Now: / compares the ORM to the live schema and goes 503 on drift, so monitoring pages. /ready stays 200, so Kubernetes doesn’t empty the Service mid-fix.

†Nobody did anything wrong: two applications, one schema, two release trains.

Source: sam-queries tests/api/test_health_endpoints.py (TestSchemaDriftContract, “the 2026-08-10 outage in endpoint form”) and src/sam/core/users.py, which maps the users.deactivate column the same cutover added. The columns were pdb_modified_time and idms_sync_token. The same readiness reasoning as Part 3’s CNPG PSA: degrade, don’t vanish.

Identity in

SAM never originates a user.

From the directory to users

†Adhoc groups, organizations and institutions take the same path into SAM.

The directory is itself fed: Fischer Identity (FI) supplies people and institutions, Google Groups the adhoc groups. Everything grey is legacy-side and George’s: the replica, the transformer and the daemon (NCAR/sam-ldap-syncd). The UCAR directory is replicated into an OpenLDAP copy on sam-app; the transformer turns its changes into .jsl files on a 60-second poll; the daemon PUTs them to legacy SAM on sam-tomcat, which reads and writes MySQL on sam-sql. SAMuel reads the result.

What the synchronizer writes

Tables

  • users (and its deactivate stamp)
  • email_address, phone
  • institution, organization, and each user’s links to them
  • adhoc_group and its members
  • gid_allocation

Shape

  • Event-driven, not cron: a quiet day is tens of requests.
  • A restart replays the backlog: thousands of PUTs.
  • Rootless podman on sam-app; George’s code.
  • SAMuel writes exactly one users column: primary_gid.

sam-queries docs/plans/SAM_LDAP_SYNCD_REFERENCE.md §1.2 and §2.4 (one replay sent 6,329 PUTs in 27 minutes). The users rule from docs/xras/PROJECT_AND_ACCOUNT_LIFECYCLE.md: no INSERT into users anywhere in src/, no User.create(), nothing writes active or locked; the only column SAMuel writes is primary_gid via User.set_primary_gid().

Signing in

People

  • Entra ID (OIDC, with PKCE).
  • Production refuses to start with the stub or LDAP login.
  • Roles and grants from the database (RBAC_SOURCE=db).

Machines

  • HTTP Basic, checked against bcrypt hashes.
  • Keys from the environment, or from api_credentials, shared with legacy.
  • Each key is held to the routes its role allows.

†SAMuel never talks LDAP itself. Its LDAP login provider is a stub that raises.

sam-queries docs/AUTHENTICATION.md and src/webapp/utils/api_auth.py. The api_credentials table is legacy’s: both stacks verify the same hashes, so a key works against either host during the overlap. RBAC: docs/plans/implemented/RBAC_DB_ROLES.md.

Allocations: XRAS

Allocations in by POST, reports back by sweep.

ARC → XRAS → SAMuel

docs/xras/PROJECT_AND_ACCOUNT_LIFECYCLE.md §1. Most university projects take this path; staff also create projects directly in the Admin dashboard, which must always keep working. Legacy SAM handled the POST until the 2026 cutover.

Incoming: six verbs

  • XRAS POSTs /api/xras/v1/actions: add, adjust, extend, supplement, transfer, update.
  • It GETs back people, requests and dates, in legacy’s byte shapes.
  • Live in SAMuel since XRAS repointed in August 2026. Legacy has had no XRAS calls since.
  • An action SAMuel can’t apply is parked for a human, never half-applied.

†“Any status other than 200/OK is considered an error.” Thanks, Steve Peckins: so a parked action still answers 200, with a different body.

sam-queries docs/xras/README.md and children. The repoint was 2026-08-24 (XRAS_TRIAGE_WEEK.md); the Tomcat census shows zero XRAS calls on legacy from 08-28. Every action is logged in xras_action_log, one of SAMuel’s own tables.

Outgoing: the sweep and the writes

  • xras_sweep, hourly: a light pass over active requests, plus a full “Approved” pass daily at 04:00 MT. It feeds the Allocations dashboard’s work queue.
  • Writes (merge a person, withdraw a request): from the webapp only, by a human, never from the CronJob.
  • Notices to PIs go out from the Notify button. The automatic version is built and switched off.

src/scheduling/tasks/xras_sweep.py; XRAS_OUTGOING_ENABLED=1 and XRAS_WRITE_ENABLED=1 in prod, the latter carried by the webapp’s env only. xras_notices ships named in SAM_TASKS_DISABLED. The write key is real: a person merge deletes an account in production with no undo, which is why tests pin it empty.

Usage in

From PBS logs to charges, and back out to PBS.

Data in, data out

In: PBS on casper and derecho feeds three pipelines into SAMuel. Out: HSG’s cron processes download from SAMuel’s API: the accounting hooks’ data, and the fairshare tree, which SAMuel builds itself. SAMuel talks to both databases: MySQL sam on sam-sql, and csg-postgres for system_status (written through the status API) and the jobs databases jobhist-sync fills. sam-admin accounting reads the jobs and writes charge summaries into sam. The loop takes a day for charges and minutes for status.

Collectors: PBS to the status pages

  • On each host, a script snapshots PBS into a spool directory.
  • The same samuel image parses the spool and POSTs /api/v1/status/…: Casper and JupyterHub from casper, Derecho from derecho.
  • Every 5 minutes, with a key that may post status and charge summaries, nothing else.
  • Lands in system_status on the CNPG primary, where the Status dashboard reads it.

sam-queries collectors/README.md (spool mode: run-manifest.sh on the host, –spool in the container). The key is API_KEYS_COLLECTOR, granted the api_collector role (MANAGE_SYSTEM_STATUS and MANAGE_CHARGE_SUMMARIES; src/sam/security/rbac_defaults.py), enforced under RBAC_SOURCE=db.

Job history and charges: ORM, not REST

Job history

  • jobhist-sync reads PBS accounting logs into derecho_jobs and casper_jobs.
  • Rapid every 5 min, a daily 2-day upsert, a weekly 14-day one.
  • SAMuel reads them through the read-only replica (My Jobs).

Charges

  • sam-admin accounting --comp rolls jobs into daily summaries, hourly (2 days) and daily (7 days).
  • Disk: the daily acct.<fs> files, from casper. Tracks Campaign, Destor, Quasar.
  • Archive: none currently (deprecated).

†The rapid sync looks at today’s scheduler log. The infrequent longer sweeps fill in holes over midnight or around downtimes.

‡The REST route POST /api/v1/charge-summaries/… exists too. Nobody calls it.

containers/ncar-hpc-deploy/jobs/*.sh. Charges are written straight into sam-sql through the ORM, as the lane’s database user; the REST path in docs/apis/CHARGING_INTEGRATION.md is documented but unused. Why job history left SAM at all is Part 2’s story.

The first five answer byte-for-byte like legacy, from hand-built dicts. That code is frozen on purpose; everything new declares its output with a schema. Legacy paths are under /api/protected/admin. The identity chain

Identity enters from the UCAR directory through the legacy-side synchronizer, along with the hpc group definitions (born in Google Groups). Project groups go back out two ways: legacy SAM feeds them to the UCAR directory (Ben, 2026-10-07), and directory_access hands them to the HPC LDAP provisioner, which writes unix groups into the HPC hosts’ LDAP, bob. Nicknames: the UCAR directory is filip, its replica on sam-app is stella. sam/provisioning.py compares what SAM believes against what a host actually provisions.

The identity chain, host by host

The identity chain, host by host: dashed boxes are the machines each piece runs on.

The same chain with every piece on the machine it runs on. sam-app holds the replica (stella), the transformer and sam-ldap-syncd; sam-tomcat holds legacy SAM; sam-sql holds the sam database; SAMuel runs as pods on CIRRUS. filip is the UCAR directory, bob the HPC hosts’ LDAP.

SAMuel to PBS, in one slide

  • HSG’s cron processes call SAMuel’s API. None of our Python runs on their hosts.
  • Accounting hooks: projects, users, status, queues and exemptions, from the legacy-shaped endpoints.
  • fairshare: /api/v1/fairshare/<machine> returns the PBS tree ready-made. fsparsetree_mr runs inside the API, so nobody installs it on a scheduler host.
  • HSG installs: swapping the database is free; a new tree costs a scheduler pause.
  • fsparsetree_mr comes from the hpc-scheduling-tools plugin, by design: it is developed in parallel with SAMuel, and can be swapped out when needed.

†The full story, with the trees, is the SAM & PBS deck, in this same repo.

The outbound half of data in / data out. HSG’s cron downloads from SAMuel; it does not run SAMuel code. The hooks’ database is built from fstree_access, queue and wallclock_exemption (hpc-scheduling-tools docs/PBS_HOOKS.md). fsparsetree_mr lives in hpc-scheduling-tools (NCAR, private) and is loaded as the HPC_SCHEDULING_TOOLS plugin behind /api/v1/fairshare (src/webapp/api/v1/fairshare.py), which reads the fstree data straight from SAM’s database. The sam_and_pbs deck covers the fairshare model, the queue-stuffing work, and “When Something Looks Wrong”.

Everything else

The side-channels, and the overlap mapped.

Everything else SAMuel calls

Service For When

All configured in sam-queries helm/values.yaml. Mail is fail-closed (NOTIFY_ENABLED defaults off everywhere but the prod chart); a failed Jira filing falls back to mail. The award lookups power sam-search awards. No test may open an SMTP socket or make an outbound request.

The overlap, mapped

  • Next: the ldapsync endpoints move to SAMuel. Identity’s grey box shrinks to the daemon.
  • By decision: AMIE (idle) and HEUV (not ported): port, replace, or retire.
  • Last: the schema. Once nothing grey writes sam-sql, it comes under migrations, and Postgres in production becomes possible.

†Until then, SAMuel is a careful tenant in a shared house.

The order is a dependency chain, not a calendar. Horizon 2 in docs/plans/implemented/POSTGRES_MIGRATION.md (prod on csg-postgres) is gated on retiring legacy SAM; so is putting the SAM schema under Alembic. Part 5 is where SAMuel itself runs.

TL;DR - integrations

  • Four flows: identity in, allocations both ways, usage in, access out.
  • Legacy SAM is still running, and identity still flows through it.
  • One database, two apps: we don’t own the schema yet, and it has bitten us once.
  • Usage comes in from the HPC lanes through the ORM; access goes out through legacy-shaped APIs.
  • Every grey box has a planned exit, in a fixed order, ending with the schema.
