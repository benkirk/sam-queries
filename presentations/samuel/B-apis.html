APIs & Why Two Dialects

The APIs: what callers can count on, and how we add to them.

One front door

  • 111 routes in six families: core, legacy shapes, fairshare, XRAS, identity sync and HEUV. Part 4 has the table.
  • Two ways in: a browser session, or an API key over HTTP Basic. Every read takes either.
  • Each key holds only the permissions it was granted, route by route, and most are limited to 120 requests a minute.
  • Errors look alike: {"error": "…"} with the usual status codes, or legacy’s {"errorMessage": "…"} on legacy’s own paths.
  • Docs: docs/apis/, and api-demo/: a runnable example for every family (two slides on).

Route counts are decorator counts on origin/staging, 2026-10-10 (src/webapp/run.py:441-463): core 39, legacy shapes 21, fairshare 1, XRAS 11, identity sync 26 (/api/protected/admin), HEUV 13 (/api/protected/heuv/v1). There is no /api/v2. The two /api/protected families check legacy’s role names (ROLE_API_ADMIN, ROLE_API_HEUV) rather than a Permission; ldapsync is exempt from the limiter (one sequential caller, replays peak ~350 PUTs/min), HEUV rides the 200/min authed tier. login_or_token_required (src/webapp/utils/api_auth.py): keys are bcrypt-hashed, and a good check is cached because bcrypt costs ~260 ms. Under RBAC_SOURCE=db (prod) a key needs a samuel_role_grant for the route’s Permission; there is no blanket grant (api_legacy retired 2026-10-10, #790), so the PBS key holds api_systems_integration and little else. Every v1 GET takes a key since #791. RATELIMIT_M2M is 120 per minute, counted in Redis. docs/apis/: SYSTEMS_INTEGRATION_APIs.md, HPC_DATA_COLLECTORS_GUIDE.md, CHARGING_INTEGRATION.md; api-demo/ (bash and Python per endpoint, smoked in CI).

The old dialect: no client change

  • Legacy’s JSON, at a new address. Same keys, same nesting, same camelCase.
  • A client changes its base URL and its key. Nothing else.
  • Frozen on purpose: additive changes only, and never to the bytes a client already reads.
  • Fstree, queues, wallclock exemptions, directory and project access, disk quotas, XRAS, the identity sync, and the HEUV portal feed.
  • The two newest keep legacy’s path too, so a caller changes only its host.

†XRAS is held tightest: compared byte for byte, because a swapped first and last name keeps the same length.

Part 4’s “Same bytes, new address” maps each route to its legacy path. CLAUDE.md, “Legacy-compat blueprints — DO NOT REFACTOR”. The one XRAS relaxation: masters[] is sorted rather than in Java HashMap order. Repointed: XRAS (2026-08-24, no legacy calls since 08-28). ldapsync and HEUV answer at legacy’s own paths (/api/protected/admin/…, /api/protected/heuv/v1/…); neither caller has repointed yet.

Proving it

  • A parity harness asks both hosts the same questions: about 40 rules, per endpoint.
  • Disk quotas: 590 of 590. The other gaps were a row or two of mirror lag.
  • Byte-identical was the proof. Now that callers have moved, an explainable difference beats copying a legacy bug.
  • Example: legacy picked one of a user’s duplicate phone rows at random. We pick the same one every time.

utils/parity/check_legacy_apis.py (+ comparators.py, clients.py, README.md): not pytest; it hits SAMuel and sam.ucar.edu over the VPN, –api directory|project|fstree|queue|wallclock|xras. Rules are mostly one-directional (legacy is a subset of new), with count tolerances for mirror lag. Results table: docs/apis/SYSTEMS_INTEGRATION_APIs.md. The phone fix is MIN() (src/sam/queries/directory_access.py:185-188); it reproduces legacy’s choice on real data. Other explained differences: a soft-deleted allocation counted (ufsu0023), a start_date bound on queues, a NULL commission_date treated as commissioned. Ben, 2026-09-02: “explainable differences are acceptable now”.

src/sam/schemas/disk_quota.py:13-21 (allow_none trimmed), the reference (CLAUDE.md, “Output shaping”). Its consumer is DASG; legacy path dasg/diskquota. directory_access split-and-assemble: legacy’s one join fanned each user out ~14x into ~135K rows; now one DISTINCT membership query plus small bulk lookups merged in Python: 1.5 s to 0.38 s on a production copy; 6.9 s in prod before (2026-09-02). Benchmark: tests/perf/test_directory_access_latency.py, make perf. Deep nested trees (fstree, wallclock) stay hand-built: the documented exception.

Two more, same path

  • The identity sync and the HEUV portal feed: legacy’s paths, roles, realm and bytes.
  • Schemas inside: the first two ports built to the bridge rule from the start.
  • Proven before anyone calls: HEUV matches legacy on 13 of 14 route groups in production. ldapsync loads the same records as legacy, type for type, and accepted 1,341 of 1,343 replayed writes; the other two are legacy’s own 400s.
  • Nobody calls them yet. Each caller repoints its host when ready; legacy stays the rollback.

†HEUV parity caught one of ours: a stale disk snapshot added ~1,100 TB to one project. Legacy was right, so we fixed it, here and on the dashboards.

HEUV: src/webapp/api/heuv/, src/sam/schemas/heuv.py, contract docs/apis/HEUV_API.md; parity docs/plans/HEUV_API_PORT.md § 7.2 (42 projects, 60 users; the 14th group is one charge total that moved between the two fetches). Writes follow the web app’s rules

  • Same path as a click: a form schema checks the input, then one transaction, then the same sam.manage function the dashboard calls.
  • Example: POST /projects/<code>/members reuses the Add Member form and function.
  • So a new write is cheap when its dashboard route is thin: about 15 lines.
  • About 87 of 160 dashboard writes qualify. Five have an API twin today.

sam.schemas.forms (AddMemberForm, EditAllocationForm), management_transaction (audit logging), sam.manage. docs/plans/HTMX_API_READINESS.md is the census: ~87 clean, ~46 glue, ~15 stuck, ~11 UI-only; eight extraction clusters, allocation exchange flagged as security-relevant. Existing writes: project members (POST/DELETE, PUT admin), PUT allocations, POST charge-summaries, the status collectors.

Cached, and how to refresh

  • Responses live for 5 minutes in a shared cache, one entry per query string.
  • Need it fresh? Each /api/v1 legacy-shaped endpoint has POST …/refresh:
curl -X POST -u "$SAM_API_USER:$SAM_API_PASS" "$SAM_API_BASE/api/v1/queue/refresh"
  • HSG’s tools refresh, then download. SAMuel’s own queue edits clear that cache.
  • Admins clear by category: sam-admin cache --refresh.

†The fstree for every resource takes about 2.8 s to build, and comes back at once from the cache.

CACHE_DEFAULT_TIMEOUT=300; Redis in production (CACHE_REDIS_URL), shared across workers and pods; @cache.cached(query_string=True). Refresh routes: directory_access, project_access, fstree_access, queue, wallclock_exemption, plus disk_quota and the status family. The admin route is POST /api/v1/admin/cache/refresh?category=flask|chart|usage|scans|jobs|awards|xras_api (SYSTEM_ADMIN). invalidate_queue_cache() is called by the admin queue edits. hpc-scheduling-tools’ fsparsetree_mr posts v1/fstree_access/refresh before it reads. Fairshare takes ?clear_cache=1. api-demo/systems-integration/ reads each API, then posts its refresh. ldapsync and HEUV are not cached. The 2.8 s is docs/apis/SYSTEMS_INTEGRATION_APIs.md:572 (one resource ~0.7 s); Appendix C has the prod cold-miss and read-model numbers.

api-demo: every call, written out

  • A directory you can hand over: api-demo/ at the repo root. Tar it, share it; it needs bash, curl, jq and python3.
  • Every example twice: a full curl … | jq, and a standard-library Python twin, one comment per call.
  • Laid out like this appendix: rest/, systems-integration/, ldapsync/, xras/.
  • Run on every PR: CI starts the stack, mints a key and runs all 32. ./run_all.sh is the same smoke test, against any host.
  • Reads, plus cache refreshes. SAM_API_BASE has no default, so a shared copy never clears production’s caches by accident.

†In production a key reaches only what it was granted: the CI key gets everything, the PBS key gets the systems feeds.

PRs #790 (retire the api_legacy blanket), #791 (every v1 GET takes a key), #792 (api-demo/ and its CI leg). api-demo/README.md has the layout, the auth model and what is left out. Need more? Ask.

  • Still on an old endpoint? It keeps working. Moving is a URL change.
  • Want something legacy never gave you? Ask. It comes in the new dialect, or in a legacy shape if your tooling expects one.
  • We can do the computing: the fairshare tree comes ready-made, so nobody runs the builder on a scheduler host.
  • Next on our side: repointing the ldapsync and HEUV callers, a shared paging helper, and an OpenAPI spec.

Aimed at HSG and groups like them: teams tied to old endpoints, or who would want more but have not asked. Honest state of the new dialect: paging is hand-rolled per route (only projects and users page), and there is no OpenAPI yet (api-demo/ is the worked examples, not a spec); both are on the fix-later list in the plan (SAMUEL_PRESENTATION.md §14). Cutovers: docs/plans/LDAPSYNC_DEV_SHADOW.md (the exit criteria) and docs/plans/HEUV_API_PORT.md § 12.

TL;DR - two dialects

  • The old dialect is legacy’s JSON at a new address (the newest two at the same path): no client change, frozen.
  • Proven by parity, and an explainable difference beats a copied bug.
  • The new dialect is snake_case, paged, and declared in schemas; legacy shapes built today use schemas too.
  • Writes reuse the web app’s rules, so new ones are cheap.
  • Cached for five minutes, with a refresh for when that’s too long.
  • Every call has a worked example (api-demo/), run on every PR.
  • The API is where SAMuel grows: if you need more, ask.
